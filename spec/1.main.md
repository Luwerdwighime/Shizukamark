# Общее
- Приложение стеганографии Flutter
- Название "Shizukamark"
- Поддерживаемые платформы: Android.
- Поддерживаемые платформы позже: iOS, Linux, Windows, macOS (только архитектурный задел, билды в CI отключены)
- Библиотеки и зависимости:
  - ffmpeg (через ffmpeg_kit_flutter_new)
  - file_picker
  - path_provider + path
  - sqflite
  - permission_handler
  - flutter_localizations + intl
  - Riverpod 2.x (state management)
- Мультиязычность: основной язык пока русский (он же по умолчанию). Английский генерируется простым машинным переводом строк. Все строки через ARB.
- Код на GitHub (https://github.com/Luwerdwighime/Shizukamark). Все сборки, проверки и релизы — через чистые GitHub Actions (см. раздел #CI/CD).
- State management: Riverpod.
- Структура проекта:
```
  lib/
    core/          # crypto, stego, audio_pipeline, key_format
    data/          # db, repositories
    domain/        # models, use-cases
    l10n/          # localization
    presentation/  # screens, widgets, modules
  spec/            # Technical specification (это ТЗ)
  .github/workflows/  # CI/CD
```
- Все тяжёлые операции (ffmpeg, stego) выполняются в Isolate / compute(). Показывается прогресс.
- Все ошибки ядра возвращают типизированный Result. Toast только на уровне UI.
- Permissions: permission_handler (Android 13+ READ_MEDIA_AUDIO и т.д., iOS document picker).
- Минимальная версия Android (minSdkVersion): 24 (обеспечивает поддержку Android 10 / API 29 и совместимость с ffmpeg_kit_flutter_new).
- Target Android SDK (targetSdkVersion / compileSdkVersion): 34.
- Версия Java для сборки: 17.
- Версия Flutter SDK: 3.27.x (channel stable).
- Работа с файлами на Android 10+ (API 29+): для сохранения и чтения внешних файлов использовать системный File Picker (SAF - Storage Access Framework) через пакет `file_picker` без прямого обращения к пути `/storage/emulated/0/...`.
- Все пути, возвращаемые Keys и принимаемые StegoProcessor/Audiowmark, всегда относительные от getApplicationDocumentsDirectory() и начинаются с "keys/".
- Абсолютные пути используются только внутри Audiowmark (для бинарника) и внутри AudioProcessor (для временных файлов).

# Пользовательский смысл
- юзер1 генерирует ключ в нашей программе.
- вводит секретное сообщение и записывает его хэш в звуковой файл.
- злоумышленник пережимает файл другим кодеком.
- юзер1 экспортирует свой zip с ключами и сообщениями.
- юзер2 получает от юзера1 zip сторонним способом и импортирует его в программу.
- юзер2 в нашей программе извлекает секретное сообщение из звукового файла, пользуясь своей библиотекой ключей и сообщений.

===

# Девелоперский смысл
- Мы - графический интерфейс, audiowmark - наш внешний инструмент стеганографии, остальной функционал из Flutter репозиториев.
- Мы обеспечиваем менеджемент ключей и секретных сообщений локально для обеспечения кроссплатформенности, носим с собой необходимые инструменты (обеспечиваем статически линкованный бинарник audiowmark под нужную платформу).
- Мы обеспечиваем экспорт и импорт рабочих данных (секретные сообщения, хэши, файлы ключей), необходимых для решения юридических задач музыкантов по стеганографии музыки. Тогда как audiowmark обеспечивает саму стеганографию.

# Ядро

## Операции на запуске
- При запуске в getApplicationDocumentsDirectory() создаётся папка keys, если отсутствует, с правами 770.
- Там же создатся таблица `messages.sqlite`, если отсутствует.
- Директория исполняемых бинарников (для Android): при старте бинарник `audiowmark` из `assets/android/bin/` распаковывается в `getApplicationSupportDirectory()` (директория с правом исполнения `exec`), где ему выставляются права `chmod 755`.

---

## База данных SQLite (таблица messages)
Таблица `messages` должна иметь следующую структуру:
- `id` INTEGER PRIMARY KEY AUTOINCREMENT
- `msg` TEXT NOT NULL (секретное сообщение)
- `hash` VARCHAR(32) NOT NULL (хэш секретного сообщения)
- `ts` INTEGER NOT NULL (Unix timestamp в миллисекундах)

- Располагается в getApplicationDocumentsDirectory() в `messages.sqlite`.
- msg - обычный непустой printable Unicode любой длины.
- hash должен быть строго 32 hex-символа lowercase ([0-9a-f]{32}). Генерируется в режиме "Нанести знак".
- При вставке (создание или импорт) проверять:
  - msg непустой printable Unicode;
  - hash соответствует regexp;
  - при совпадении hash — игнорировать строку (не обновлять, не дублировать).
- Требуется класс-обёртка Messages по работе с таблицей, его функции обязаны проводить соответствующие проверки как при создании сообщений в нашей программе, так и при импорте zip.

---

## Работа с архивом ключей
- Папка keys в getApplicationDocumentsDirectory() - это хранилище ключей, которое хранит их в виде стандартных файлов .key формата audiowmark (описываемого ниже).
- При создании и при импорте всегда генерируется новое уникальное имя файла.
- Имя файла ключа: 8 hex-символов (SHA-256 от 16 случайных байт) + расширение ".key".
- При существовании файла — генерировать имя заново.
- Файлы должны быть доступны бинарнику audiowmark на чтение, а папка на запись свежего файла ключа.
- keyPath, который возвращает Keys и принимает StegoProcessor/Audiowmark — **относительный** путь вида `keys/a1b2c3....key`.
- Требуется класс-обёртка Keys по работе с ключами, он должен стать интерфейсом для кода более высокого уровня.
- Класс Keys предоставляет:
  - `Future<List<KeyInfo>> listKeys()  // KeyInfo = {String name, String keyPath}`
  - `Future<KeyInfo> createKey(String name)`
  - `Future<void> deleteKey(String keyPath)`
- При удалении ключа файл просто удаляется; сообщения в БД не затрагиваются.

### Файл .key
- В каждом файле ключа есть строка, начинающаяся с "key" - в её втором поле лежит hex-like ключ (без кавычек). Он нам не нужен, его читает audiowmark.
- В каждом файле ключа возможна строка, начинающаяся с "name" - в ней лежит имя ключа (в кавычках). Если такой строки нет, то имя считаем пустой строкой.
- Коду более высокого уровня нужны данные об именах ключей и их фактических путях. Класс Keys должен их предоставлять в виде массива структур {name, keyPath}, т.к. name нужен UI, а keyPath нужен audiowmark.

## Создание zip для экспорта (zipOut)
- Создаётся zip-архив со следующей структурой в корне:
```
  keys/           # все файлы *.key
  messages.sqlite
```
- Полученный файл сохраняется, по указанному родительской функцией пути.

---

## Импорт zip (zipIn)
- Проверяется наличие в корне zip:
  - файла `messages.sqlite`.
  - папки keys/ (может быть пустой).
- `messages.sqlite` распаковывается во временный файл в getTemporaryDirectory(), после импорта удаляется.
- Каждая строка messages добавляется через Messages (с проверками). Дубликаты hash статистически невероятны.
- Все *.key из keys/ копируются в нашу папку keys с новыми уникальными именами. Содержимое файлов .key обслуживаем не мы.
- При любой ошибке структуры — Result.error("zip архив с неправильным содержимым").

## Аудио-процессор (abstraction)
Нужен для будущего ухода от нестабильной ffmpeg_kit_flutter_new.

```
abstract class AudioProcessor {
  Future<void> decodeToPcm(String inPath, String outPath);
  Future<void> encodeFromPcm(String inPath, String outPath, {required AudioCodec codec});
}
```

- decodeToPcm: любой поддерживаемый формат → WAV PCM 16-bit, sample rate и каналы как в исходнике
- encodeFromPcm:
  - AAC: -c:a aac -b:a 192k
  - Opus: -c:a libopus -b:a 128k
  - MP3: -c:a libmp3lame -b:a 192k
  - FLAC: -c:a flac
  - WAV: -c:a pcm_s16le
  - ALAC: -c:a alac
- Все операции в Isolate.

---

## Процессор стеганографии
Нужен для последующего расширения инструментов стеганографии.

```
abstract class StegoProcessor {
  Future<void> add(String inPath, String outPath, String hash);
  Future<String> get(String inPath, Bool patient);
}
```
Сейчас рализация этого абстракта через Audiowmark.

## Прогресс операций

### Дизайн прогресса операций
- UI показывает всплывающее окно:
  - Сверху список операций. После выполненных операций с выравниванием по правому краю появляется чёрная UTF галочка для светлого фона.
  - Снизу один LinearProgressIndicator (0.0…1.0). Под ним текст "Выполняется "+ toLowerCase(названиеОперации).
  - Кнопка «Отмена» в прогресс-диалоге:
    1. Вызывает Isolate.kill(priority: Isolate.beforeNextEvent) или CancelableOperation.cancel().
    2. Удаляет in.wav и out.wav.
    3. Закрывает диалог.
- Список операций для наложения водяного знака: "Декодирование аудио", "Наложение водяного знака", "Кодирование аудио".
- Список операций для считывания водяного знака: "Декодирование аудио", "Чтение водяного знака".

### Механизмы прогресса операций
- Операции для наложения и чтения водяного знака выполняются последовательно, используя разные механизмы:
  - Кодирование и декодирование аудио выполняется средствами Flutter, через абстракт AudioProcessor. Его, как тяжёлую операцию, следует выполнять в отдельном потоке.
  - Наложение и чтение водяного знака выполняется средствами внешнего к Flutter бинарника audiowmark через абстракт StegoProcessor. Его, как тяжёлую операцию, тоже следует выполнять в отдельном потоке.

### Временные файлы прогресса операций
- Нет способа быстро совместить эти разные по природе компоненты (библиотеку и бинарник), кроме как через временные файлы.
  - При декодировании всегда генерируется свежий временный getApplicationDocumentsDirectory()+"/in.wav".
  - При наложении стего audiowmark всегда генерирует свежий getApplicationDocumentsDirectory()+"/out.wav".
  - И только при кодировании мы создаём файл по просьбе юзера где-то за пределами getApplicationDocumentsDirectory().
- При старте любой операции водяного знака оба файла удаляются (если существуют).
- При успехе/ошибке/отмене — оба файла удаляются.

### Поток данных
- Частота дискретизации, количество каналов и разрядность берутся из заголовка исходного файла, сохраняются вдоль всей цепочки преобразования и остаются на выходе. Из параметров исходного файла измениться может только кодек.
- Создание: AudioProcessor - in.wav - audiowmark - out.wav - AudioProcessor.
- Чтение: AudioProcessor - in.wav - audiowmark - отчёт.

## Result
typedef Result<T> = ({T? value, String? error});
- Успех: (value: ..., error: null)
- Ошибка: (value: null, error: "точный текст")
- Все методы Keys, Messages, AudioProcessor, StegoProcessor, zipIn/zipOut, Audiowmark возвращают Future<Result<...>>
- Toast показывается только на уровне UI из error.

# Прочее

## Валидация пользовательского ввода в UI
Все текстовые поля, куда пользователь что-то вводит (секретное сообщение, имя ключа):
- непустая строка
- только printable Unicode
- длина (кроме секретного сообщения) от 1 до 128 символов включительно. При нарушении — соответствующий toast / подсветка ошибки, действие не выполняется.

## Работа с ошибками
- Все файловые операции, операции с БД, запуск audiowmark - операции низкого уровня - обёрнуты в соответствующие классы, что даёт изоляцию и чёткие классы возможных ошибок.
- Весь код высокого уровня перехватывает сообщения от ядра программы и адекватно реагирует на них регулярно отсвечивая в UI соответствующие toast.
- Юзер получает строгие IT формулировки ошибок без упрощения смысла (иногда, включая log-репорты), юзер - профессионал в музыке, у него всегда есть IT консультант.
